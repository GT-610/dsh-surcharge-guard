# dsh-surcharge-guard

Some providers charge more for long prompts even when the request still fits the model's context window. Set a surcharge threshold for the exact provider and model without altering the context window.

## Configure protection

Open **Plugins → Surcharge guard**. Enter a rule manually, or prefill suggestions for matching GPT, Gemini, or Grok model IDs. New rules start enabled, so one takes effect as soon as it is added; the prefilled threshold is only a suggestion and should be checked against the provider's pricing.

Each rule's status column carries a switch and a state badge, and a disabled rule's provider and model are dimmed. The table header offers one **Enable all / Disable all** button plus an enabled count, so a prefilled batch can be turned on in one step.

The guard starts checking at `max(1, surcharge threshold − safety margin)`. A larger margin triggers earlier. The retain ratio sets the largest recent-history budget, as a fraction of that trigger, and the guard keeps less when the gap demands a deeper fold.

The summary attempt limit bounds attempts that did not help. An attempt that fails, or one whose fold does not lower the measured pressure, counts against it for the rest of the turn. A fold that does lower the pressure resets the count, so a long turn that keeps growing back over the trigger is folded again rather than going unprotected until the next user message; `0` disables guard compaction and the hard line. A spent budget only stops soft attempts: the hard line has its own forced fold and refusal, described below.

**Hard surcharge line.** Native compaction can treat the context window as a hard boundary because the provider rejects an over-window request; the model's own limit is the enforcement. Nothing rejects a surcharge line, so the guard has to enforce it locally. After the soft attempts, if the request is still priced at or above the line, the guard mirrors native overflow recovery: it prunes tool results (model-free), forces one depth-zero fold that bypasses the attempt budget and the retained-tail policy, and if the request is still over, refuses to dispatch it. The turn ends with a `SurchargeLineError` and no provider call, which is the only way to guarantee the higher rate is not paid. The last gate sits on the `llm/stream` waterfall and reprices the exact outgoing messages and tool schemas, so a system-prompt refresh or late context admitted after the pre-step cannot slip past the line; compaction summaries are exempt because they are the recovery mechanism itself. `enforceLine: false` restores the earlier warn-only behaviour.

**Why not set the model context window to 272K.** Native compaction's threshold is `min(window × 0.8, window − maxTokens − 65536)`. A 272K window with a 128K output reservation and the default headroom leaves `272,000 − 128,000 − 65,536 = 78,464` tokens, so native compaction folds at about 78K and churns far below the intended line. The guard keeps the adapter's real window and enforces the surcharge line separately, which is what the line is: a billing boundary, not a model capacity.

## What happens before a step

The guard matches the selected route, measures the committed history, and adds an estimate for the messages admitted for that step. `measure()` reports the last provider count plus content appended since that request, priced at the fixed four-characters-per-token heuristic; that delta is exactly where a route with a denser tokenizer undercounts. `surfaceTokens − surfaceDeltaTokens` reconstructs the heuristic price of the history the provider count covers, so the quotient is the route's observed expansion factor. The guard prices the surface delta and the admitted messages at that factor, per route and per session. A larger observation applies at once and a smaller one is released by ten percent per step, so one noisy call cannot relax the margin; without a provider count behind the measurement the factor stays at one. A step another middleware already folded — native pressure compaction runs in the same middleware chain — is left alone: a second transaction there could only rewrite the checkpoint the first one wrote. Otherwise the guard chooses one span. The verbatim tail is the retain ratio narrowed toward a floor when the recorded pressure sits so far above the trigger that the ratio would keep everything worth folding. A span holding nothing but the checkpoints earlier folds wrote, or whose reclaim would not cover the replacement, is refused and reported instead of compacted. The guard then delegates to the agent preset's compaction service (or a root backend where applicable), preserves the leading system message and tool pairs, and measures again after the summary. One transaction per soft step: a residual gap below the line is reported, not chased. At the line the guard may force one deeper fold before it blocks. Only the backend records compaction events.

A rule may name a summary model. That route cannot be passed through `compactRegion`, which takes only a range, an agent and a signal, and the Basic backend keeps its summary route in instance state. So the guard mounts one Basic instance inside a fresh `compaction` realm for that transaction and disposes it afterwards: concurrent sessions never share or overwrite a route, and the session's own backend is never rebound. The class comes from the backend the preset already mounted, and the summary budget is inherited from the routed policy. A backend without Basic's summary settings is reported instead of being replaced; a failed route warns and does not fall back. Another provider receives the selected history and the summary request's prompts and tool definitions.

A rule may also name a reasoning effort for that summary model. Basic's own configuration cannot carry one — its loader rejects unknown keys in `resolveConfig`, and the summarizer builds each request itself — so the effort rides on the `llm` service the engine resolves. The guard nests an isolated `llm` scope inside the transaction's `compaction` realm and provides an effort-bound view of it before starting the backend, so only that transaction's summary call is affected and the shared service is never replaced.

The view reports no tracker on purpose. A tracked service is re-wrapped for every reader, and that re-wrap resolves `stream` from the prototype descriptor, which would discard the override and silently send the route's default effort instead. Forwarding the tracker "for correctness" breaks the feature without failing anything else, so the hidden symbol is load-bearing rather than dead code. Binding every function also replaces `constructor` with a bound wrapper, so the view's `constructor` is not the runtime class; `instanceof` still holds, and nothing in the harness dispatches on either.

The route and its effort are validated through `llm.resolveCallConfig` before the transaction opens, so an unsupported level becomes one warning and that compaction never runs — no marker pair, no summary request, and no attempt spent against the per-turn limit. The effort is route-owned in the settings page, which drops it when the summary model changes; the config layer keeps whatever a hand-edited route carries and the pre-flight check rejects it. The effort appears only once a custom summary model is chosen; DSH's own summary settings, manual compaction and the chat route keep theirs.

Raising the effort spends part of the summary's output cap, not a separate allowance. Basic documents `maxTokens` as covering "any provider-counted reasoning tokens", and it treats a `max-tokens` finish as a truncated, incomplete checkpoint. The guard inherits that cap from the routed policy of the guarded model, so a summary model given a small cap plus a high effort can spend the budget thinking and never finish the checkpoint. That summary fails, the step continues uncompacted, and the attempt is spent — the same shape as any other summary failure, and it reports `truncated at the token cap` rather than blaming the level. Validation cannot prevent it: the level is supported, there is simply not enough room left to emit it. A cap comfortably above the effort's thinking budget avoids it, which is why the default headroom is usually enough.

The estimate is not the final provider token count. Below the line, an unhelpful fold leaves the step decision unchanged and reports the problem in the host log; a refusal costs no attempt, so it is reported once per turn instead of once per step. At the line the guard fails closed instead: it prunes, forces one deep fold, and rejects the step if the projection still does not fall. A separate summary request can incur charges. The attempt limit does not cover native DSH compaction or the backend's internal retries.
